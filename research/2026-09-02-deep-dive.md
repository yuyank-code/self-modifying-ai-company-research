# Deep Research Pass — 2026-09-02

## 1. Field thesis

Self-improvement should be modeled as an update operator over an agent configuration. The configuration can include the foundation model, prompts, memory, tools, planner/controller, executable code and deployment configuration. The most practical near-term systems modify the scaffold around a fixed model; weight-level or open-ended recursive improvement is a later capability.

The July 2026 survey *Self-Improvements in Modern Agentic Systems* explicitly organizes the field by update target and signal and distinguishes foundation-model improvement from scaffold improvement. This is an important conceptual anchor for the company's architecture.

Primary source: https://arxiv.org/abs/2607.13104
Survey hub: https://selfimproving-agent.github.io/

## 2. Recursive self-improvement is not one problem

A useful decomposition is:

### Behavior loop
Agent observes an outcome, critiques it, and tries again. Already practical.

### Artifact loop
Agent stores a successful strategy as memory/skill/tool. Practical and cheap.

### Scaffold loop
Agent edits prompts, routing, workflow graphs, evaluators and executable logic. Increasingly practical.

### Software loop
Agent modifies source code, executes tests and deploys validated changes. Practical within constrained environments.

### Model loop
Agent fine-tunes/adapts/replaces model components. Possible but more expensive and data/compute dependent.

### Research loop
System chooses what to investigate, creates experiments, evaluates results and determines future research directions. Early but rapidly advancing.

### Open-ended RSI
System autonomously redesigns its entire successor without externally fixed evaluators/constraints. Not demonstrated as a reliable general capability and should not be the initial company assumption.

The 2026 recursive-self-improvement survey emphasizes that evaluator design is a bottleneck and distinguishes bounded self-refinement from open-ended RSI. https://arxiv.org/abs/2607.07663

## 3. Strong evidence of practical AI development loops

Anthropic's 2026 report describes AI taking an increasing role in its own development. It reports that more than 80% of code merged into Anthropic's codebase was authored by Claude by May 2026, while also explicitly noting that lines of code are an imperfect productivity metric. It further describes experiments where Claude repeatedly rewrote and benchmarked optimization code against a fixed goal. This is close to a bounded self-improvement loop: fixed objective + candidate modification + execution + measurement + iteration.

Source: https://www.anthropic.com/institute/recursive-self-improvement

Commercial implication: our first system should copy the *loop structure*, not claim the much stronger ability of autonomous open-ended self-design.

## 4. Self-evolving agent architectures

Gödel Agent is important because it demonstrates a self-referential architecture in which an LLM can dynamically modify its own logic/behavior under a high-level objective. The work reports continuous improvement across multiple domains.

Source: https://aclanthology.org/2025.acl-long.1354/

Research question for us: which parts of this architecture can be converted from a research demonstration into a production-safe control plane with independent evaluation, rollback and provenance?

## 5. Evaluation is the central infrastructure opportunity

LangChain's June 2026 survey of 1,300+ professionals reports 57% of respondents with agents in production, 32% identifying quality as a top barrier, nearly 89% implementing observability and 52% implementing evaluations.

Source: https://www.langchain.com/state-of-agent-engineering

This creates an opportunity between observability and autonomous improvement. Existing observability tells a team what happened. Our proposed system should answer: **what should change, did the change actually help, can we prove it, and can we safely deploy it?**

Potential category: **Agent Improvement Infrastructure**.

The University of Washington's 2026 agentic-browser work finds that security behavior differs significantly between browsers and that prompt injection can potentially enable cross-origin attacks in less restrictive architectures.

Sources:
- https://blog.google/security/prompt-injections-web/

## 10. Proposed technical architecture

### Agent Genome
Versioned representation of:
- model identifier
- system/developer instructions
- prompt templates
- tools and schemas
- tool permissions
- memory policies
- retrieval configuration
- workflow graph
- planner/controller
- code modules
- environment configuration
- evaluation suite

### Improvement Engine
Generates candidate mutations to selected genome components.

### Experiment Sandbox
Runs candidates with:
- CPU/GPU quotas
- network restrictions
- filesystem isolation
- secret isolation
- deterministic fixtures
- synthetic adversarial inputs

### Evaluation Engine
Combines:
- unit tests
- task success
- regression tests
- security tests
- latency
- cost
- quality graders
- independent verifiers

### Promotion Controller
Candidate is promoted only if policy criteria are met.

### Production Monitor
Tracks drift, regressions and unexpected behavior.

### Rollback Manager
Keeps previous versions immediately recoverable.

### Provenance Graph
Records which experience produced which candidate, what tests it passed, and where it was deployed.

## 11. Improvement algorithm

A production-safe abstract loop:

1. Collect trajectory and outcome.
2. Detect failure or optimization opportunity.
3. Generate N candidate modifications.
4. Reject candidates violating static policies.
5. Run candidates in isolated evaluation environments.
6. Compare against the current baseline and an independent evaluator.
7. Run adversarial/regression tests.
8. Select only improvements meeting threshold and confidence requirements.
9. Canary deploy.
10. Monitor.
11. Roll back automatically if guardrails fail.
12. Store the result as an improvement artifact.

This is essentially CI/CD for agent intelligence.

## 12. Important design principle: optimize the evaluator before optimizing the agent

If an agent can modify itself but also controls the evaluator, it can learn to satisfy the measurement rather than the real objective. Therefore:

- evaluator versions should be independently controlled
- high-impact evaluators should be partially independent from the candidate generator
- holdout tasks must remain hidden
- security tests should not be editable by the agent
- metrics should be multi-dimensional
- randomization and adversarial tests should prevent narrow gaming

This is a potential research moat: **trusted improvement measurement**.

## 13. Browser/web strategy

Universal browser control is attractive as a demo but weak as the initial enterprise substrate because web pages are hostile, dynamic, authenticated and semantically ambiguous. API/MCP/tool integrations are more deterministic.

Recommended hierarchy:
1. First-party API.
2. Structured tool/MCP interface.
3. Browser automation only when no reliable API exists.
4. Human confirmation for high-impact irreversible actions.

The company can still build self-evolving websites as a later application of the same improvement control plane.

## 14. Database strategy

A self-modifying database should initially mean adaptive database *management*, not unrestricted schema mutation.

Candidate changes:
- index recommendations
- query-plan optimization
- caching policies
- partitioning recommendations
- data-quality rules
- retrieval/ranking configuration
- schema migration proposals

The system should create migration candidates, replay workloads, compare performance/correctness, and require controlled promotion.

## 15. Self-evolving website strategy

A practical version is:

User behavior -> hypothesis -> generated UI/logic variant -> synthetic/browser tests -> accessibility/security tests -> A/B or canary deployment -> outcome measurement -> promotion/rollback.

The website is therefore not literally rewriting itself freely. It is participating in a governed evolutionary optimization loop.

This distinction makes the idea far more commercially credible.

## 16. Large-company lessons

### NVIDIA
Core transferable lesson: own a substrate. CUDA succeeded because developers built software on top of a consistent platform, supported by libraries, tools, hardware and ecosystem effects. Our analogue would be a common runtime/evaluation/provenance layer that developers use to make many different agents adaptive.

Core lesson: distribution matters. Azure + GitHub + developer tooling gives Microsoft access to the workflow where software is created. Our product should integrate into GitHub/CI/CD/IDEs rather than require teams to replace their development stack.

Microsoft's 2025 annual report describes Azure AI Foundry as a unified platform for developers to design, customize and manage AI applications and agents. https://www.microsoft.com/investor/reports/ar25/

### Google/DeepMind

Source: https://deepmind.google/blog/co-scientist-a-multi-agent-ai-partner-to-accelerate-research/

### Palantir

## 17. Company architecture

The long-term company can be divided into five layers:

1. **Adaptive Runtime** — execution and modification.
2. **Improvement Cloud** — experiments, evaluation, versioning and rollout.
3. **Trust Layer** — identity, policy, security, audit and provenance.
4. **Developer Ecosystem** — SDK, CLI, GitHub/CI integrations, APIs and marketplace.
5. **Applications** — coding, operations, customer support, data, web and enterprise workflows.

The company should own layers 1-3 first and use applications as distribution wedges.

## 19. First technical MVP

Build a GitHub-native agent that can maintain a controlled repository.

Input: issue + repository + tests + allowed permissions.

Baseline agent executes the task.

Adaptive runtime records trajectory and failures.

Improvement engine proposes a change to one of:
- prompt
- tool choice
- workflow
- code strategy
- memory/skill

Candidate is tested on the original task plus hidden regression tasks.

If it passes, candidate becomes version 2.

Then run version 2 against future tasks and measure whether improvement persists.

The demo should show a timeline:

v1 -> failures -> hypothesis -> v2 -> tests -> improvement -> deployment -> monitoring.

This is much more convincing than a demo where an LLM merely writes code.

## 23. Falsification criteria

The company thesis should be abandoned or revised if:
- adaptive changes do not produce persistent improvements over strong static baselines
- gains disappear when controlling for extra inference budget
- evaluators are too easy to game
- maintenance cost exceeds human maintenance
- customers do not pay for the measured improvement
- foundation-model providers absorb the entire improvement layer
- security constraints make autonomy economically unusable
