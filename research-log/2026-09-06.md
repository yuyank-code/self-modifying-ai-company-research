# Deep Research Pass — 2026-09-06

## Executive summary

Today's pass moved the program from category-level research into **implementation archaeology**: reconstructing what the strongest current self-improvement systems actually modify, how they search, how they evaluate candidates, what remains fixed, and where the commercial abstraction differs from the research prototype.

The strongest conclusion is now more precise:

> The commercially defensible opportunity is unlikely to be an autonomous agent that rewrites itself. It is more plausibly a **portable control plane for governed AI evolution**: a system that represents an agent/application as a versioned state, proposes mutations, runs them in isolated environments, evaluates both performance and capability changes, promotes only policy-compliant candidates, and records the complete improvement trajectory.

This conclusion is strengthened by three independent directions:

1. Palantir AIP Evolve has already productized a governed improvement loop for Foundry AI systems.
2. OpenAI's internal Codex usage shows that the practical bottleneck is increasingly supervision, environment design, feedback loops and long-horizon orchestration rather than merely generating code.
3. Research systems such as Darwin Gödel Machine, Hyperagents, AREX and Red Queen Gödel Machine are pushing the research boundary from static agents toward systems that improve either their task policy, their improvement process, or their evaluators.

Therefore our differentiation must move upward: **portable improvement infrastructure + independent verification + capability governance + longitudinal improvement data**.

## 1. Implementation archaeology: Darwin Gödel Machine

### What DGM actually changes

The Darwin Gödel Machine (DGM) is not an abstract claim that an AI "improves itself." It operates over an executable coding-agent implementation.

The published mechanism is:

1. Maintain an archive of existing agent variants.
2. Select an existing agent from the archive.
3. Ask a foundation model to produce an interesting modified version.
4. Execute/evaluate the candidate on coding benchmarks.
5. Add promising candidates to the archive.
6. Repeat, allowing future candidates to inherit from previously successful variants.

The search space therefore contains actual agent implementation choices such as code-editing tools, context handling, peer review and other scaffold-level mechanisms. DGM reported SWE-bench improvement from 20.0% to 50.0% and Polyglot improvement from 14.2% to 30.7% in the paper's experiments.

Primary source: https://arxiv.org/abs/2505.22954

The public implementation exposes a useful architecture for our purposes: `coding_agent.py`, `DGM_outer.py`, prompts, tools, tests, benchmark runners and experiment logs are separated. The repository explicitly warns that model-generated code is untrusted and should be executed with safety precautions.

Source: https://github.com/YazanGhafir/self-improving-agent-dgm

### What this proves

**High confidence:** code-level agent scaffolds can be searched and empirically improved under a sufficiently verifiable task.

**Medium confidence:** open-ended archive-based exploration can outperform a single greedy improvement chain.

**Low confidence:** this establishes general open-ended recursive self-improvement outside domains where the evaluation function is cheap and reliable.

### Important limitation

DGM's strongest setting is coding because coding provides unusually strong validators: tests can execute, patches can be compiled, and benchmarks can score outcomes. This is a special property of software, not a generic property of intelligence.

This makes coding an exceptionally important initial commercial wedge.

## 2. Hyperagents: the meta-level itself becomes mutable

Hyperagents extend the DGM idea by combining the task agent and the meta-agent in a single editable program. The critical change is that the mechanism responsible for generating improvements can itself be modified.

Primary source: https://arxiv.org/abs/2603.19461

The conceptual hierarchy becomes:

`task solution -> task-agent improvement -> improvement-process improvement -> improvement-process-of-improvement`

This matters because a normal optimizer assumes its optimization procedure is fixed. Hyperagents make the optimizer itself part of the search space.

### Commercial implication

We should **not** initially expose unrestricted meta-level mutation to customers. Instead, represent the improvement engine as a set of versioned operators:

- mutation operator
- candidate selector
- evaluator selector
- memory compressor
- experiment scheduler
- promotion policy

Each operator should have a separately versioned interface.

That allows us to eventually research self-modifying improvement algorithms while keeping enterprise deployments governed.

## 3. AREX: discovery and verification should be separate loops

AREX studies recursive self-improvement for deep research.

Primary source: https://arxiv.org/abs/2607.21461

Its key architectural insight is a **discovery-verification asymmetry**:

- discovering a useful answer can be expensive and open-ended;
- checking whether a candidate satisfies individual constraints can often be made much cheaper and more structured.

AREX alternates an inner research loop with an outer audit loop and maintains a compact improvement state containing verified evidence and unresolved constraints.

### Generalization to our platform

Every Improvement Job should have two distinct planes:

**Exploration plane**
- generate candidates
- search alternatives
- mutate prompts/workflows/code
- explore model/tool combinations

**Verification plane**
- test correctness
- check regressions
- check security
- check capability delta
- compare cost/latency
- validate provenance

The verification plane should be harder to modify than the exploration plane.

This is more than a safety principle. It is a **product architecture boundary**.

## 4. Red Queen Gödel Machine: fixed evaluators may become the wrong abstraction

The Red Queen Gödel Machine (RQGM) explicitly challenges the assumption that the evaluator remains stationary while the agent improves.

Primary source: https://arxiv.org/abs/2606.26294

The paper introduces controlled utility evolution in epochs: the evaluation criterion is fixed within an epoch, but can change at epoch boundaries. It also co-evolves agents and evaluators.

Reported results include improved coding performance, better paper-writing acceptance under diverse judges, and better grading accuracy. Importantly, the work also reports that a strong baseline reviewer could over-accept AI-generated papers at up to 1.91x the human rate, and adversarial objectives were used to find reviewers that were more equally stringent on AI and human work.

### Why this changes our evaluation design

A naive improvement platform would be:

`agent -> evaluator -> score -> mutation`

A more robust platform needs:

`agent -> evaluator ensemble -> adversarial evaluator -> hidden tests -> real-world outcome`

and periodically:

`new evidence -> evaluator audit -> evaluator revision -> frozen epoch`

This suggests a future product category within the company:

**Evaluation Governance / Evaluator Lifecycle Management.**

The company could eventually sell not only agent improvement but trusted evaluation infrastructure.

## 5. A crucial distinction: optimizing the agent vs optimizing the environment

Today's research identified four independent levers that can produce apparent "improvement":

### A. Agent improvement
The agent genuinely becomes better.

### B. Search improvement
The system simply tries more candidates or spends more inference compute.

### C. Evaluator adaptation
The metric becomes easier to satisfy.

### D. Environment leakage
The candidate obtains information or privileges that make the benchmark easier without improving general capability.

A credible research result must separate these.

Therefore every experiment should report:

`quality gain / extra inference cost / evaluator changes / environment changes / capability changes`

rather than only benchmark score.

`designing the environment in which agents can reliably produce and validate code.`

This strongly supports the control-plane thesis.

```text
AgentGenome

├── model
│   ├── provider
│   ├── model_id
│   ├── version
│   └── inference_parameters
├── instructions
├── memory

│   ├── semantic

│   └── retention_policy
├── tools
│   ├── definitions
│   ├── routing
│   └── permissions
├── workflow
├── planner/controller
├── executable_code
├── environment
├── evaluator_suite
├── security_policy
├── deployment_policy
└── provenance_parent
```

Every improvement produces:

`parent_genome -> candidate_genome`

rather than an opaque "new agent."

This enables reproducibility, rollback and cross-model comparison.

## 8. Capability Delta becomes a first-class security artifact

A candidate should additionally emit:

```text
CapabilityDelta
├── new_tools
├── removed_tools
├── changed_permissions
├── filesystem_delta
├── network_delta
├── credential_delta
├── data-access delta
├── deployment delta
├── evaluator-access delta
└── agent-spawning delta
```

Promotion then becomes two independent decisions:

### Performance promotion
"Did this candidate improve the target objective?"

### Authority promotion
"Is this candidate allowed to possess the capabilities it now has?"

These must never be merged into one score.

A candidate could have +15% benchmark performance and still be rejected because it requested unrestricted network access.

This is a major potential differentiator from research-only self-improvement systems.

## 9. The Promotion Transaction

A useful abstraction emerged today: **agent improvement should behave like a transaction.**

An Improvement Job should have:

```text
BEGIN
  snapshot parent genome
  generate candidates
  sandbox candidates
  evaluate candidates
  calculate capability deltas
  verify policies
  select candidate
  canary deploy
  observe
COMMIT
```

or:

```text
ROLLBACK
```

This creates a direct analogy to databases and CI/CD.

### Potential core primitive

`promote(candidate_id, policy_id, evidence_bundle)`

The promotion service verifies:

- parent exists
- candidate is reproducible
- evaluator version is trusted
- hidden tests passed
- capability delta is permitted
- security policy passed
- provenance is complete
- deployment target matches policy

Only then can the candidate become active.

## 11. Memory should be treated as mutation, not as the whole product

Microsoft Foundry's 2026 Agent Service explicitly separates procedural, user and session memory. Microsoft reports early Tau-bench gains from procedural memory.

Source: https://devblogs.microsoft.com/foundry/whats-new-in-microsoft-foundry-build-2026/

This supports the taxonomy:

- session memory = context continuity
- user memory = persistent facts/preferences
- episodic memory = prior experiences
- semantic memory = knowledge
- procedural memory = learned ways of doing work

For our architecture, the important distinction is:

**memory itself can evolve.**

A failed trajectory can generate a candidate procedural rule. But that rule should pass the same evaluation/promotion process as a code change.

Therefore:

`memory mutation = governed agent mutation`

This makes memory part of the unified improvement substrate rather than a separate product.

## 12. Coding remains the best initial domain for a deep reason

Coding has an unusual property: it provides an environment where the improvement objective can often be mechanically checked.

For software:

- syntax can be parsed
- builds can execute
- unit tests can run
- integration tests can run
- static analysis can run
- security scanners can run
- benchmarks can run
- behavior can be replayed
- deployments can be canaried
- rollback is comparatively straightforward

For a general business process, these properties are weaker.

Therefore the initial company should probably not start as a universal self-improvement platform.

It should start with a **high-verifiability domain** and generalize outward.

Coding is the strongest current candidate.

## 13. Browser agents: the verification problem becomes harder

Web environments have weaker determinism:

- pages change
- content is adversarial
- authentication expires
- external state changes
- websites contain untrusted instructions
- tool responses can be malicious
- real actions may be irreversible

VeriEnv proposes recreating websites into executable, resettable and programmatically verifiable environments.

Source: https://verienv.com/

### Strategic implication

A future platform should distinguish:

**Development Environment**
- deterministic
- resettable
- synthetic or cloned
- unrestricted experimentation inside sandbox

**Production Environment**
- real identities
- real credentials
- real consequences
- restricted mutations
- mandatory policy checks

This is analogous to software staging environments, but applied to agent behavior.

Potential product: **Agent Staging / Agent Simulation Infrastructure.**

AAAI 2026's BAMAS research explicitly treats multi-agent topology as an optimization problem under a compute budget. It reports comparable performance while reducing cost by up to 86% on evaluated tasks.

Source: https://ojs.aaai.org/index.php/AAAI/article/view/40226

This is potentially more commercially valuable than simply making a model smarter because it directly affects gross margin.

## 15. Cost must be part of the objective from day one

An agent that improves task success from 70% to 80% while increasing cost by 10x may be economically worse.

Therefore define a multi-objective utility:

`U = quality - λ(cost) - μ(latency) - ν(risk) - ρ(intervention)`

The exact weights should be customer-specific.

This means the Improvement Control Plane should optimize **business utility**, not benchmark accuracy alone.

Possible objective templates:

- maximize success subject to cost ceiling
- minimize cost subject to success floor
- minimize latency subject to quality floor
- maximize reliability subject to security constraints
- migrate model while preserving behavior
- reduce human intervention

This matches Palantir AIP Evolve's product direction, which already exposes goals such as model migration, cost reduction, latency reduction and eval improvement.

Source: https://www.palantir.com/docs/docs/foundry/announcements

## 22. Experiment matrix

### E1 — Mutation-surface ablation

Compare:

- prompt only
- memory only
- tools only
- workflow only
- code only
- combined

Goal: determine where most commercial improvement actually comes from.

### E2 — Search vs intelligence

Hold the model fixed and vary:

- number of candidates
- inference budget
- search depth
- archive size

Goal: determine whether apparent improvement is simply more compute.

### E3 — Evaluator independence

Compare:

- same model generates and evaluates
- separate model evaluates
- deterministic tests evaluate
- ensemble evaluates

Goal: measure evaluator gaming.

### E4 — Capability Delta

Allow mutation with and without explicit capability analysis.

Goal: quantify how often performance improvements require unwanted authority.

### E5 — Cross-model portability

Take the same improvement artifact and apply it to multiple models.

Goal: test whether the platform owns reusable intelligence or merely model-specific tricks.

### E6 — Improvement Graph prediction

Train a predictor over historical trajectories.

Question:

Can previous failure->fix->outcome patterns predict which future mutations are worth testing?

If yes, this could become a significant data moat.

### E7 — Longitudinal evolution

Run 100+ improvement generations.

Track:

- improvement saturation
- regressions
- evaluator drift
- diversity collapse
- capability creep
- archive diversity
- cost explosion

This is essential because short benchmark experiments can hide long-horizon failure.

## 28. Contradictions and negative evidence

### Contradiction 1
Self-improvement works impressively in coding, but coding has unusually strong verification. General intelligence remains much harder to evaluate.

### Contradiction 2
The more capable the system becomes, the more valuable unrestricted experimentation becomes—but also the more dangerous it becomes.

### Contradiction 3
Independent evaluators improve trust, but sophisticated systems can potentially manipulate evaluators or exploit correlated blind spots.

### Contradiction 4
Open protocols increase ecosystem adoption, but the most valuable improvement data may need to remain proprietary.

### Contradiction 5
More search can produce higher benchmark scores without increasing underlying intelligence.

### Contradiction 6
A large company can reproduce much of the platform internally. Therefore the startup needs an ecosystem/network-effect advantage or specialized cross-platform data advantage.

These contradictions remain active research questions.
