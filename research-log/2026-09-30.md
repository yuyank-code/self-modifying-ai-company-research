# Research Log — 2026-09-30

## Frontier
The program is moving from architecture design into executable evolution infrastructure.

## New evidence

### Recursive Harness Self-Improvement
Lee et al. (2026) report iterative prompt-level harness refinement that raises performance and can reduce inference cost on synthetic ML-research tasks.
Source: https://arxiv.org/abs/2607.15524

### AIDE^2
Srikanth et al. (2026) report an 8-day autonomous loop where an AI research agent modifies its own code, evaluates modified versions on hidden evaluations and retains successive improvements.
Source: https://arxiv.org/abs/2609.26457

### RRSI
Xia et al. (2026) report regularized harness evolution with stronger held-out transfer and lower policy-token cost than unregularized evolution.
Source: https://arxiv.org/abs/2609.24972

### ModularRSI
Wu et al. (2026) use benchmark-disjoint evolution and restricted functional modules, reinforcing EvolutionScope and modular attribution.
Source: https://arxiv.org/abs/2609.14857

### VeRO
Ursekar et al., ICML 2026, introduce versioning, budget-controlled evaluation and structured execution traces for agent-harness optimization.
Source: https://proceedings.mlr.press/v306/ursekar26a.html

## Revised conclusion
The key question is no longer whether bounded harness/skill self-improvement is possible. Current work provides evidence that it is.

The unresolved infrastructure question is whether one externally governed protocol can make these loops reproducible, independently evaluated, transferable, cost-accountable, security-bounded, reversible and composable.

## Decision
Proceed with Common Evolution State Machine v1.1 and build a model-agnostic reference implementation.

## Caution
Reported results remain task-, benchmark-, model- and selection-dependent. Open-ended weight-level RSI and unrestricted successor redesign remain unestablished.

## Next frontier
Implement schemas, immutable snapshots, sandbox execution, evaluator registry, external acceptance, EvolutionCommit lineage and canary/rollback simulation.


## 2026-09-30 platform-security addendum
MCP should be treated as an execution and authority boundary, not merely a tool protocol. The current specification treats tools as potentially arbitrary code execution paths and requires consent and authorization controls. The platform should therefore place its Authority Plane above MCP and record tool/server identity, capability, resource audience, actor identity, policy decision, provenance and side-effect class.

Two 2026 MCP issue reports add threat-model inputs: possible public-cache poisoning and server-controlled instruction injection. These are issue reports rather than independent validation, so confidence is medium-low, but they justify adversarial testing of discovery metadata and caching.

CUDA lesson: the durable moat is an ecosystem, not a single runtime. NVIDIA combines libraries, frameworks, enterprise software, infrastructure, partner hardware and distribution. An adaptive-software equivalent needs portable Artifact, Evolution, Evidence, Authority, Evolution-Commit, Replay, Deployment and Distribution contracts.

E113: freeze model, evaluator, authorization policy and MCP servers; evolve only routing/context management; test malicious tool descriptions, poisoned resources and cross-tenant requests. Measure task success, verified improvement yield, unauthorized calls, privilege escalation, injection susceptibility, cost and rollback integrity.

Commercial implication: prioritize a trusted adaptive-runtime control plane for evidence, safe evolution, authorization, rollback and cost accounting across existing agents, models and tools.
