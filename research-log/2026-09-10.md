# Deep Research Pass — 2026-09-10

## Executive update

This pass moved the program from the abstract idea of self-improvement toward implementation archaeology and a sharper platform thesis: **verified evolution infrastructure**. The strongest new evidence is that the field is converging on a common loop—agent/harness change, executable evaluation, archive/versioning, and bounded promotion—while major vendors are productizing pieces of that loop. The remaining differentiation opportunity is the cross-vendor control plane: independent evaluation integrity, capability-delta analysis, provenance, promotion/rollback, and an improvement graph that can itself become a learning asset.

## 1. Implementation archaeology: the loop is already reproducible

Several open-source implementations now expose the mechanics rather than only describing self-improvement conceptually.

### Darwin Gödel Machine implementations

A current open-source DGM implementation supports multiple frontier-model providers, Bash/file tools, an agent archive, benchmark-driven evolution, lineage visualization, and guarded execution with workspace-scoped access, command filtering, timeouts and optional Docker isolation. It explicitly separates controller, agent, archive, evaluation and self-modification components. The repository reports the paper's SWE-bench trajectory of roughly 20% to 50% and polyglot improvement around 14.2% to 30.7%.

Source: https://github.com/lemoz/darwin-godel-machine

A second implementation, darwinloop, makes the control loop even more explicit: benchmark tasks define the objective; each generation produces a unified diff; every generation is retained in an immutable JSON archive; sandbox execution is subprocess-isolated; network is unavailable in the sandbox; regression protection keeps only strictly improving candidates; and human checkpoints can be enabled. A small router benchmark reported 51% to 80% accuracy over five iterations.

Source: https://github.com/ShyamRV/darwinloop

**Architectural finding:** a minimal self-improvement engine does not require weight updates. It can operate entirely over executable agent state.

## 2. The commercial moat cannot be 'self-editing code'

The existence of multiple open implementations means code mutation itself is rapidly becoming an available primitive. Meta's HyperAgents research explicitly notes that coding is unusually favorable because both the target task and the self-improvement process can be expressed as code; it also warns that this alignment does not generally hold beyond coding.

Source: https://ai.meta.com/research/publications/hyperagents/

Therefore the startup should not compete on the claim that it can edit agent code. It should compete on the infrastructure around that capability.

## 3. New core platform abstraction: Improvement Job

A useful API-level object is an **Improvement Job** containing:

- baseline agent/version
- objective function
- hard quality constraints
- cost ceiling
- latency ceiling
- allowed mutation classes
- forbidden mutation classes
- maximum iterations
- evaluation suite
- hidden holdout policy
- capability policy
- deployment target
- canary policy
- rollback policy

This turns self-improvement from an autonomous behavior into a governed transaction.

Example conceptual job:

`maximize task_success; quality>=0.98; cost<=1.2x; latency<=1.1x; permissions=unchanged; mutations={prompt,workflow,skill}; iterations<=20; hidden_tests=true; auto_rollback=true`

This is a potentially portable primitive across OpenAI, Anthropic, Google, open-source and custom agents.

## 4. Evaluation integrity is a first-class security subsystem

Reward-hacking research continues to show that improving the visible metric can diverge from actual quality. A May 2026 study on rubric-based RL found that weak verifiers can produce large proxy-reward gains that do not transfer to reference evaluators; even stronger verifiers did not eliminate reward hacking when rubrics omitted important failure modes. The paper also identifies a 'self-internalization gap' that can diagnose when optimization against a weak verifier stops producing real quality improvement.

Source: https://arxiv.org/abs/2605.12474

The architectural consequence is that a promotion system needs:

- multiple evaluator families
- hidden holdouts
- immutable evaluator versions
- evaluator access isolation
- adversarial tests
- out-of-distribution checks
- real-world outcome checks
- evaluator-tampering telemetry

**New rule:** the candidate generator and the final authority over promotion should be separate trust domains.

## 5. Microsoft validates the evaluation/control-plane direction

Microsoft Foundry now supports continuous custom evaluators, agent monitoring, monitoring of agents that run outside Foundry, batch evaluations for third-party agents, safety evaluations, custom policies and recurring red-team scans.

Source: https://devblogs.microsoft.com/foundry/whats-new-in-microsoft-foundry-apr-2026/

This demonstrates that enterprise customers are being taught to think of evaluation and observability as production infrastructure rather than one-time model testing.

**Competitive implication:** evaluation dashboards alone are insufficient. The differentiation has to be the transaction that connects evaluation to controlled improvement and promotion.

## 6. New evidence for the 'persistent learning' wedge

A July 2026 study describes a production coding-agent deployment where human review feedback is converted into persistent behavioral rules. Across 11 recorded sessions on a 35+ service microservice platform, the rule set grew from 5 to 18 behavioral rules plus language-specific standards and a self-review checklist; the authors report 0% recurrence for error classes explicitly captured by the rules.

Source: https://arxiv.org/abs/2607.13091

This is strategically important because it suggests a much lower-complexity commercial wedge:

**human feedback -> persistent behavioral rule -> automatic self-check -> reduced recurrence**

before attempting autonomous code mutation.

## 7. Existing commercial self-improvement

Anthropic's partner material describes Warp building agents that learn from how teams correct them and rewrite their own skills. The examples include PR review and community-management workflows.

Source: https://www.anthropic.com/webinars/how-warp-builds-self-improving-agents-on-claude

This means persistent skill evolution is already entering commercial agent products. It reinforces the need to climb from 'learning skills' toward verified cross-system evolution infrastructure.

## 8. AI research loops are moving upward

Anthropic reports a bounded open-ended research experiment in which Claude agents proposed hypotheses, ran experiments, shared findings and iterated. The agents reportedly recovered 97% of the gap between a weak supervisor and a strong-model ceiling over roughly 800 cumulative hours and about $18,000 of compute. The authors explicitly caveat that humans still chose the research problem and scoring rubric and that transfer to production-scale models was imperfect.

Source: https://www.anthropic.com/institute/recursive-self-improvement

The important distinction is:

**AI can increasingly execute a research loop when humans define the outer objective and measurement boundary.**

This is evidence for bounded research automation, not proof of unrestricted recursive self-improvement.

## 9. Safety implication: improvement must be reversible

Current DGM implementations independently converge on guarded execution, immutable archives, rollback and bounded execution. This is not accidental engineering detail. It suggests reversibility is a basic primitive of self-improvement.

A production platform should therefore treat promotion as a transaction:

`candidate -> verify -> capability check -> canary -> commit`

with an always-available:

`commit -> rollback -> previous known-good version`

path.

## 10. Capability Delta becomes a separate promotion axis

Every candidate should produce a machine-readable delta describing changes to:

- tools
- network access
- filesystem access
- credentials
- databases
- process spawning
- evaluator access
- deployment permissions
- agent spawning

A candidate can have:

`performance=PASS`

and simultaneously:

`authority=FAIL`

The system must reject it.

This is more fundamental than ordinary benchmark regression because self-modification can alter the system's ability to affect the world, not merely its task accuracy.

## 11. NVIDIA platform lesson: ecosystem, not algorithm

NVIDIA's current Rubin platform shows the modern platform strategy: compute, networking, security, systems software and an extensive partner ecosystem are presented as one AI-factory stack. NVIDIA explicitly emphasizes trusted isolation for multi-tenant agentic workloads through BlueField-4 and its security architecture.

Sources:
- https://investor.nvidia.com/news/press-release-details/2026/NVIDIA-Kicks-Off-the-Next-Generation-of-AI-With-Rubin--Six-New-Chips-One-Incredible-AI-Supercomputer/
- https://investor.nvidia.com/news/press-release-details/2026/NVIDIA-Vera-Rubin-Ramps-Into-Full-Production-to-Power-Agentic-AI-Factories-Worldwide/default.aspx

The transferable lesson is that a CUDA-like position requires a stack: API, runtime, adapters, libraries, security, profiling/debugging, deployment and ecosystem—not merely an improvement algorithm.

## 12. Meta's XR agent work reveals a generalizable verification pattern

Meta's July 2026 XR SDK includes Meta XR Operator, allowing coding agents to inspect a running VR/MR application, interact with it, capture screenshots, drive inputs, and diagnose intentionally broken scenes. This closes a loop between code changes and validation in a live environment.

Source: https://developers.meta.com/horizon/downloads/package/meta-xr-core-sdk/

This is a useful pattern for future self-evolving applications:

`modify -> run -> observe real system -> diagnose -> modify`

The general platform opportunity is to make that loop standardized across environments.

## 13. Important theoretical contradiction: deployment changes the problem

Google DeepMind's June 2026 paper 'Solipsistic superintelligence is unlikely to be cooperative' argues that deployment itself creates endogenous non-stationarity: the environment changes in response to the AI, causing a train-test-deploy gap. It proposes dynamic evaluation with adaptive counterparties and institutions as design primitives.

Source: https://deepmind.google/research/publications/231466/

This is a major challenge to our current benchmark-centric thinking.

A candidate can pass every static test and still fail because:

`agent changes world -> world changes -> previous evaluation distribution becomes invalid`

Therefore the eventual platform needs **adaptive evaluation environments**, not only static test suites.

## 14. Updated capability taxonomy

L0 behavioral self-refinement
L1 memory/skill evolution
L2 routing/tool adaptation
L3 workflow/planner adaptation
L4 code/harness evolution
L5 application/infrastructure evolution
L6 model-component/weight adaptation
L7 architecture/topology evolution

Current evidence remains strongest through bounded L4. L5-L7 are promising but fragmented. L8 is not a reliable demonstrated capability.

## 15. New company architecture

### Layer 1 — Evolution Runtime
Executes candidate versions under controlled permissions.

### Layer 2 — Improvement API
Defines Improvement Jobs and mutation policies.

### Layer 3 — Evaluation Integrity
Independent, hidden, versioned and adversarial evaluation.

### Layer 4 — Capability/Trust Layer
Identity, authority, Capability Delta, secrets, policy and audit.

### Layer 5 — Promotion/Deployment
Canary, commit, rollback and drift detection.

### Layer 6 — Improvement Graph
Causal memory of failures, hypotheses, mutations and outcomes.

### Layer 7 — Developer Ecosystem
SDK, adapters, CLI, registry, integrations and marketplace.

Applications become distribution wedges rather than the entire company.

## 16. First MVP recommendation updated

The lowest-risk path now appears to be a two-stage product:

### MVP-A: Persistent Agent Learning
Convert human corrections into versioned behavioral rules and measure recurrence reduction.

### MVP-B: Verified Evolution
Allow bounded automated mutation of the agent harness, with protected evaluation and rollback.

This sequence gives the company a path from an immediately useful product to the deeper research thesis without requiring open-ended self-modification from day one.

## 17. Benchmark program

Primary benchmark: **Verified Improvement Rate (VIR)**.

A candidate counts only if it:

1. improves visible tests
2. improves hidden tests
3. persists on future tasks
4. generalizes outside the optimization set
5. passes capability policy
6. cannot modify evaluation authority
7. stays within cost constraints
8. stays within latency constraints
9. passes security checks

Secondary metrics:

- persistent improvement rate
- regression rate
- unauthorized capability rate
- evaluator-tampering rate
- improvement cost
- human intervention rate
- improvement latency
- cross-task generalization
- rollback frequency

## 19. Strategic conclusion

The strongest current thesis is not:

'Build an AI that modifies itself.'

It is:

**Build infrastructure that makes AI evolution measurable, secure, reversible, portable and economically useful.**

The likely first wedge is coding because code provides unusually strong executable validation. The long-term platform should be model- and framework-neutral and should treat evaluation integrity, authority changes and causal improvement history as first-class primitives.

## 20. Contradictions / falsification conditions

The thesis must be weakened or abandoned if:

- foundation-model vendors absorb the entire evolution layer
- persistent learning gives most of the value without autonomous mutation
- Improvement Graph history does not improve candidate generation
- hidden evaluations cannot prevent proxy optimization
- capability isolation creates unacceptable operational cost
- adaptive evaluation becomes too expensive to run continuously
- customers do not pay for reduced maintenance/intervention
- portable infrastructure provides less value than vertically integrated vendor stacks
