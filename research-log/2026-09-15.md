# Self-Modifying AI Company Research — 2026-09-15

## Executive finding

Today's pass adds a new failure mode to the platform thesis: **self-improvement under a changing harness is itself a distinct continual-learning problem**. A system can improve its internal skill/memory/policy while becoming worse when tools, skills, specialist agents, or other externally supplied harness components change. This means a commercially viable evolution platform needs to optimize two objectives simultaneously: **adaptation to new capability** and **retention of old competence**.

## 1. New benchmark: EVOHARNESSBENCH

EVOHARNESSBENCH (arXiv 2609.04280, September 7, 2026) evaluates agents while the externally supplied harness evolves across tools, skills, and specialist agents. It contains 17 deterministic multi-stage harness streams, 802 tasks, 520 tools, 42 skills, and 62 agents. It separates deployment evaluation (retaining old competence as the harness expands) from self-evolving adaptation (using accumulated experience to exploit new capabilities).

The reported result is important: harness expansion alone can cause **harness-induced forgetting**; self-evolving gains are inconsistent across stages/axes/environments; and retention and adaptation can pull in opposite directions. Source: https://arxiv.org/abs/2609.04280

### Company implication

The Agent Genome cannot be treated as the complete state. We need an explicit **Harness Compatibility Contract**:
- harness version;
- tool schemas;
- skill versions;
- specialist-agent versions;
- routing map;
- capability inventory;
- compatibility tests;
- migration rules;
- rollback target.

Every Improvement Transaction should be evaluated against both the incumbent harness and the next intended harness version.

## 2. New research direction: skills as operational knowledge

Repo-To-Skill (arXiv 2609.02749, September 2, 2026) proposes distilling GitHub repositories into compact, verified skills so research agents can reuse operational knowledge rather than rediscovering it. Its DisCo system produces task-agnostic and task-oriented skills from repositories.

Source: https://arxiv.org/abs/2609.02749

### Interpretation

This strengthens the idea that the valuable persistent state of an adaptive agent may be neither model weights nor raw conversation memory. It can be **verified operational knowledge**: compact procedures, constraints, debugging heuristics, environment assumptions, and failure patterns.

That is commercially attractive because operational knowledge can be:
- versioned;
- signed;
- tested;
- shared across models;
- revoked;
- sold as domain capability;
- audited independently of model weights.

It also suggests a future **Skill Registry** should be a first-class platform component rather than a file store.

## 3. OpenRSI has matured from paper architecture into a reproducible stack

The OpenRSI repository now exposes OpenMLE-Gym, OpenMLE-RL, OpenMLE-Evo, a distributed OpenMLE Sandbox, Frontis-MA1, datasets, and documentation for task construction, validation, launch, resume, and outputs. Its repository describes the four atomic operators Draft, Improve, Debug, and Crossover and reports 39.39% → 60.61% improvement on MLE-Bench Lite for Frontis-MA1 with OpenMLE-Evo, plus 71.21% with OpenMLE-Evo-Max.

Source: https://github.com/FrontisAI/OpenRSI

### New architectural inference

The field is converging on a separation between:
1. **operator learning**;
2. **execution environment**;
3. **long-horizon search**;
4. **evaluation**.

This is evidence for treating the Evolution Plane as a modular platform, not a monolithic agent.

## 4. Reliability taxonomy is becoming more rigorous

The September 11 survey companion "Diving into Reliable Self-Evolving Agents" organizes 549 manuscript-used papers by the deepest object being evolved and by the evidence supporting improvement. Its taxonomy distinguishes task-local evolution, model/policy state, scaffold, improver, and criterion evolution, while emphasizing that deeper evolution does not imply greater reliability.

Source: https://github.com/wkqdzkd/Awesome-Reliable-Self-Evolving-Agents

This is useful for our evidence matrix because it makes a previously blurred distinction explicit:

**evolution depth is not evidence strength.**

A criterion-changing system may be deeper than a skill-changing system but much less trustworthy.

## 5. New practical open-source signal: laptop-scale Skill RSI

The Skill-RSI repository describes a local recursive loop that studies a domain, generates or revises an Agent Skill, tests variants, and retains winners. It is explicitly designed to run on a laptop and as a Codex plugin.

Source: https://github.com/justinwetch/Skill-RSI

### Company implication

The entry barrier for experimentation is falling. Therefore a generic "self-improving skill loop" is unlikely to be a durable moat.

The moat must be in:
- trustworthy acceptance;
- enterprise integration;
- provenance;
- protected evaluators;
- capability/authority controls;
- production evidence;
- cross-model transfer;
- accumulated improvement trajectories.

## 6. New security evidence: MCP/tool poisoning is a platform-level problem

MCP threat-modeling research reports tool poisoning as a major client-side vulnerability and evaluates seven major MCP clients. MCP-ITP goes further by automatically optimizing poisoned tool metadata and reports attack success rates as high as 84.2% on MCPTox while reducing malicious-tool detection to as low as 0.3% in its tested setting.

Sources:
- https://arxiv.org/abs/2603.22489
- https://arxiv.org/abs/2601.07395

ClawGuard instead enforces task-derived rules at every tool-call boundary and reports robust protection across AgentDojo, SkillInject, and MCPSafeBench.

Source: https://arxiv.org/abs/2604.11790

### Architectural conclusion

The **Tool Registry must not be trusted merely because a model selected it**.

A production registry should contain:
- tool identity;
- publisher identity;
- signed schema;
- permissions;
- network scope;
- data scope;
- dependency graph;
- poisoning scan;
- behavioral baseline;
- evaluator coverage;
- revocation status.

This creates a potential **Agent Software Supply Chain** product layer.

## 7. New business signal: organizational context is itself an agent capability

Atlassian's September 11, 2026 announcement connects agentic development directly to Jira, Confluence, Teamwork Graph, multi-repository code context, governance, and measurement. The stated bottleneck is organizational context rather than model intelligence.

Source: https://www.itpro.com/software/development/agentic-development-workflows

### Strategic implication

The company should not build an isolated agent runtime and expect it to become indispensable. The runtime needs connectors into the systems that contain **organizational truth**:
- source control;
- issue trackers;
- docs;
- deployment systems;
- observability;
- identity;
- incident systems;
- databases.

The improvement engine then learns from the customer's actual workflow rather than synthetic tasks alone.

## 8. New current competitive signal: data governance may become a gating factor

Reuters reported September 14, 2026 that Palantir, NVIDIA and other organizations are restricting some use of external frontier models amid concerns about proprietary-data handling and retention. The report describes demands for stronger data-use guarantees.

Source: https://www.reuters.com/business/palantir-nvidia-curb-ai-model-use-over-data-fears-information-reports-2026-09-14/

This is strategically important for a neutral evolution platform: **cross-model portability is only valuable if customers can control where their data and improvement traces go.**

Therefore deployment options should eventually include:
- SaaS;
- VPC/private cloud;
- customer cloud;
- self-hosted control plane;
- air-gapped evaluator/runtime for highly sensitive workloads.

## 9. Governance is becoming a market constraint, not merely a safety feature

Anthropic's September 2026 call for third-party evaluation and Microsoft's September 14 human-control code point toward increasing demand for external accountability. These are policy signals, not technical proof of RSI, but they reinforce the product opportunity around independently auditable adaptive systems.

Sources:
- https://darioamodei.com/post/we-must-pace-the-frontier
- https://www.reuters.com/legal/litigation/microsoft-drafts-code-conduct-keep-its-ai-under-human-control-2026-09-14/

## 10. Updated architecture: Harness Plane added

Previous architecture:
Evolution / Evidence / State / Authority / Deployment.

New requirement:

### Harness Plane
Controls and versions the externally supplied capabilities that surround the model:
- tools;
- MCP servers;
- skills;
- specialist agents;
- prompts/context templates;
- routing;
- environment adapters.

The complete architecture is now:

**Evolution Plane** — operators, candidate generation, search, archive.

**Evidence Plane** — evaluators, hidden tests, acceptance, contamination/provenance.

**State Plane** — memory, skills, experience, Improvement Graph, runtime snapshots.

**Harness Plane** — tools, MCP, skills, specialist agents, routing, environment versions.

**Authority Plane** — identity, credentials, sandbox, action-boundary policy, capability/authority delta.

**Deployment Plane** — promotion, canary, monitoring, drift, rollback.

Trust/provenance and cost remain cross-cutting.

## 11. New product abstraction: Harness Migration

If harness evolution can cause forgetting, then an improvement platform needs an explicit migration workflow:

`old_harness -> compatibility analysis -> migration candidate -> regression suite -> new-capability suite -> authority audit -> canary -> promote`

This could become a commercial feature independent of RSI.

A customer could use the platform simply to answer:

> "We changed 30 tools and 8 agent skills. What broke, what improved, and what must be migrated?"

That is a much more immediate enterprise problem than autonomous self-rewriting.

## 12. New experiments E41–E48

**E41 — Harness expansion forgetting:** add tools/skills incrementally and measure old-task retention.

**E42 — Migration operator benchmark:** compare human-written migration, LLM-generated migration, and search/evolution migration.

**E43 — Skill Registry transfer:** test whether verified skills transfer across GPT/Claude/Gemini/open models without retraining.

**E44 — MCP poisoning gate:** benchmark signed/provenance-checked registry versus ordinary MCP discovery.

**E45 — Harness-aware acceptance:** evaluate candidates against both current and future harnesses.

**E46 — Private deployment economics:** compare SaaS, VPC and self-hosted evaluator costs.

**E47 — Organizational-context value:** remove/reintroduce Git/Jira/docs/incident context and quantify improvement quality.

**E48 — Improvement trajectory moat:** test whether historical customer-specific improvement trajectories improve future candidate search enough to justify proprietary storage.

## 13. Company formation update

The first product now has two independently sellable entry points:

### Wedge A — Verified Agent Improvement
Existing agent → controlled improvement → evidence → promotion/rollback.

### Wedge B — Harness Evolution Control
Existing agent ecosystem → detect capability regressions when tools/skills/models change → generate migration → verify → deploy.

Wedge B may actually be easier to sell because enterprises already experience software-change regressions, while "self-improving AI" remains a novel budget category.

The long-term platform can combine them:

**software changes + agent changes + AI changes = one governed adaptive system.**

## 14. CUDA analogy update

Today's evidence makes the CUDA analogy more precise.

CUDA succeeded because NVIDIA controlled a stable abstraction boundary across rapidly changing hardware and supplied libraries, compilers, tooling, documentation, and developer distribution.

An adaptive-intelligence platform would need an equivalent stable abstraction:

**Improvement Transaction + Evaluation Contract + Capability Contract + Artifact Contract.**

The underlying models, tools and agents could change while developers keep the same evolution API.

But unlike CUDA, we do not yet have evidence of a sufficiently universal primitive or installed base. Therefore the CUDA thesis remains **speculative**.

The realistic intermediate goal is:

**"Git/CI/CD for adaptive agents" → "platform API for verified evolution" → potential ecosystem.**

## 15. Cognitive Holobiont relevance

Harness evolution strengthens a systems-level Holobiont analogy: a distributed cognitive system would need components to change without destroying the collective's existing competencies. Retention/adaptation tradeoffs resemble stability/plasticity problems in adaptive systems.

This is a systems-engineering analogy only. No evidence in today's work establishes consciousness, biological equivalence, or a direct route from enterprise agent infrastructure to a Cognitive Holobiont.

## 16. Evidence boundary update

### Demonstrated / strong
- bounded self-evolution;
- persistent skill/knowledge adaptation;
- execution-grounded AI4AI evolution;
- harness-induced forgetting;
- MCP/tool-poisoning vulnerabilities;
- external action-boundary security;
- need for independent evaluation.

### Promising
- verified operational-knowledge skill registries;
- harness migration systems;
- cross-model skill portability;
- customer-specific improvement trajectory learning;
- agent software supply-chain infrastructure.

### Weak / unresolved
- autonomous training-algorithm redesign;
- general weight-level RSI;
- economically superior unrestricted autonomous improvement.

### Unsupported
- guaranteed monotonic open-ended RSI;
- safe unrestricted successor redesign;
- claims that current multi-agent ecosystems constitute a Cognitive Holobiont.
