# Deep Research Log — 2026-09-03

## Executive thesis update

Today's pass materially strengthens the hypothesis that the first commercially defensible layer is not unrestricted recursive self-improvement, but **governed improvement infrastructure**: software that turns agent failures and outcomes into candidate changes, evaluates those candidates independently, and controls promotion, rollback, provenance, permissions, and cost.

The important change from 2026-09-02 is that the market is beginning to expose the same primitive from multiple directions: frontier labs are building continuous security/improvement loops; enterprise platforms are making agents operationally governed; open-source projects are implementing self-evolving skills/harnesses; and NVIDIA's newly announced acquisition of Hugging Face demonstrates how valuable a developer/model ecosystem can become as an infrastructure layer.

Confidence: HIGH for the existence of these converging trends; MEDIUM for the claim that a startup can own the category; LOW for any claim that unrestricted recursive self-improvement is close.

## 1. New research: self-improvement is becoming a stack, not a feature

A useful decomposition now looks like:

1. **Trajectory improvement** — better behavior within a task.
2. **Memory/skill accumulation** — successful strategies persist between tasks.
3. **Prompt/configuration evolution** — instructions and configuration are optimized.
4. **Workflow evolution** — planning, routing and multi-agent topology change.
5. **Tool evolution** — tool choice, schemas and tool-use strategies change.
6. **Code evolution** — the agent modifies executable software.
7. **Architecture evolution** — the agent changes the structure of its own agent system.
8. **Model adaptation** — fine-tuning, preference optimization or model-component editing.
9. **Model replacement** — choosing or training a stronger successor model.
10. **Open-ended successor design** — the system determines its own future search space.

The strategic error would be to call all ten levels "self-modification." They have radically different safety, capital, latency and verification requirements.

## 2. Strong evidence: open-ended agent evolution is already experimentally real, but bounded

The Darwin Gödel Machine (DGM) is the strongest conceptual reference found in this pass. It modifies its own code, maintains an archive of generated agents, explores multiple evolutionary paths, and empirically validates changes on coding benchmarks. The published experiment reports SWE-bench improvement from 20.0% to 50.0% and Polyglot from 14.2% to 30.7%, with sandboxing and human oversight. This is significant evidence that code-level self-improvement can produce measurable gains, but it is not evidence of unrestricted autonomous intelligence explosion. The search space, benchmark, model substrate and experimental controls still constrain the system.

Source: https://arxiv.org/abs/2505.22954

Strategic implication: the first company should build the **control/evaluation machinery around this loop**, rather than betting the company on achieving open-ended RSI itself.

## 3. New evidence: architecture itself can evolve

AutoMaAS treats multi-agent architecture as a search space. It generates/fuses/removes operators, adjusts cost-aware parameters and uses online feedback to refine architectures. Across six benchmarks it reports 1.0–7.1% performance improvement with 3–5% inference-cost reduction.

Source: https://arxiv.org/abs/2510.02669

This matters because our proposed "Agent Genome" should not be limited to prompts. It should represent topology: planner, executor, verifier, specialist agents, routing rules, tool allocation, memory and fallback policy.

Research question: can topology evolution outperform simple prompt optimization after controlling for extra inference budget?

## 4. New evidence: continuous learning can combine verifier + learner + memory

SuperIntelliAgent proposes a frozen large model as verifier and a trainable smaller learner. Candidate outputs are converted into chosen/rejected pairs for DPO; short-term reasoning traces and long-term learned memory are combined with replay. The paper reports improvement across benchmarks using automatically generated preference pairs.

Source: https://arxiv.org/abs/2511.23436

This supports a major architectural distinction:

**Generator ≠ Evaluator ≠ Memory.**

A production improvement platform should make these separate objects with different trust levels. If the candidate generator can rewrite the evaluator, improvement measurement becomes suspect.

## 5. New evidence: search-based design optimization has direct economic value

AUTO treats design optimization as gradient-free search guided by LLM agents. In GPU-code optimization experiments it reports competitive solutions and 50–70% search efficiency relative to Bayesian optimization, with reported run costs below estimated human-developer costs for those experiments.

Source: https://arxiv.org/abs/2511.22651

This suggests an economically useful first principle:

> Self-improvement becomes commercially interesting before it becomes generally intelligent if it can optimize expensive engineering artifacts.

Possible early verticals:
- SQL/query plans
- GPU kernels
- test generation
- CI pipelines
- infrastructure configuration
- retrieval/ranking
- agent workflows
- codebase-specific skills

## 10. New security conclusion: self-improvement and agent security are the same control-plane problem

OpenAI's 2025 Atlas security work describes automated red teaming using reinforcement learning to discover prompt-injection exploits and then using those discoveries to improve defenses. OpenAI's March 2026 work continues to frame prompt injection as an evolving social-engineering problem for agents operating over external content.

Sources:
- https://openai.com/index/hardening-atlas-against-prompt-injection/
- https://openai.com/index/designing-agents-to-resist-prompt-injection/

This reveals a useful symmetry:

**Attacker:** generate candidate behavior that defeats safeguards.

**Improvement system:** generate candidate changes that improve safeguards.

Both require:
- a target system
- an evaluator
- a mutation/search engine
- isolated execution
- adversarial examples
- promotion criteria
- rollback

Therefore, security testing should not be a separate add-on to our architecture. It should be one of the core improvement loops.

## 12. The benchmark we should eventually own

The standard benchmark should measure not just whether an agent solves tasks, but whether it **improves itself without cheating**.

### Proposed Adaptive Agent Benchmark (AAB)

Each agent receives:
- fixed base model
- initial Agent Genome
- task distribution
- hidden holdout tasks
- cost budget
- security policy
- allowed tools

The agent can modify only specified genome components.

Measure:

### A. Immediate performance
Task success before vs after.

### B. Persistent improvement
Performance after 100+ subsequent tasks.

### C. Generalization
Performance on unseen tasks/domains.

### D. Improvement efficiency
Gain per dollar / token / GPU-second.

### E. Regression
Percentage of previously solved tasks broken by improvement.

### F. Security regression
New vulnerabilities introduced per improvement.

### G. Evaluator gaming
Performance difference between visible evaluator and hidden evaluator.

### H. Diversity
Whether successive candidates collapse into the same strategy.

### I. Human intervention
Interventions per 100 tasks.

### J. Recovery
Time/cost required to detect and roll back a bad improvement.

### K. Improvement persistence
How long the gain remains after distribution shift.

The headline metric should be:

**Verified Improvement Rate = accepted improvements that survive hidden evaluation / attempted improvements.**

A second key metric should be:

**Net Improvement Efficiency = persistent quality gain / total additional inference + training + evaluation cost.**

## 13. New architectural requirement: two-speed control system

The research increasingly supports two loops:

### Fast loop
Plan → act → observe → repair.

Milliseconds to minutes.

### Slow loop
Collect trajectories → identify recurring failure → propose genome mutations → evaluate → adversarially test → canary → promote/rollback.

Hours to days.

The slow loop should have stronger permissions than the fast loop only in the sense that it operates through a controlled change-management interface. The agent should not be allowed to bypass the promotion controller.

This resembles software release engineering more than conventional chatbot architecture.

## 19. Contradictions discovered today

### Contradiction 1
Open-ended evolution research demonstrates improvement, while production systems need predictable change control.

Resolution: treat open-ended search as the candidate-generation layer, not the deployment authority.

### Contradiction 2
Self-improvement can reduce human maintenance, but each autonomous change increases verification burden.

Resolution: optimize **net maintenance cost**, not raw autonomy.

### Contradiction 3
More autonomy increases value and attack surface simultaneously.

Resolution: permissions and security must scale with action authority, not merely model capability.

### Contradiction 4
Agent frameworks are becoming commodities while agent governance is becoming platform infrastructure.

Resolution: avoid generic orchestration as the core moat.

### Contradiction 5
Benchmarks are improving rapidly, but benchmark comparability is deteriorating.

Resolution: own a reproducible adaptive-improvement benchmark.

## 20. Important negative evidence / things not to believe yet

Do NOT conclude from current work that:

- agents can reliably redesign themselves without external constraints;
- self-modification automatically creates persistent general intelligence gains;
- benchmark improvement implies real-world improvement;
- an LLM judge is automatically an independent evaluator;
- more agent iterations necessarily improve quality;
- a self-evolving coding agent is automatically commercially defensible;
- browser agents can safely operate arbitrary authenticated websites;
- model editing provides reliable long-term knowledge updates;
- a larger multi-agent system is inherently better than a smaller one.

Every one of these remains an empirical research question.

## 23. Holobiont connection

Today's evidence strengthens only a narrow claim:

A future distributed cognitive system could be architected from specialized agents that share information, adapt locally, undergo selection, and maintain global stability through evaluation and governance.

It does NOT establish that current agent ecosystems are biological holobionts or that self-improving agents automatically become one.

The company can therefore contribute infrastructure for:
- distributed specialization
- shared memory
- communication
- local adaptation
- redundancy
- collective evaluation
- self-repair

while leaving the biological/cognitive equivalence as a separate research hypothesis.

## 25. Daily conclusion

The strongest thesis after today's research is:

> **The valuable technology is not merely an AI that changes itself. It is an infrastructure layer that makes change measurable, safe, attributable, reversible and economically useful.**

That infrastructure could eventually become a platform standard if developers use it to define, evaluate and evolve many classes of agents and applications.

The biggest unanswered question is no longer "can AI self-modify?" Experimental evidence says yes in bounded forms.

The harder and more commercially important questions are:

1. Can improvement persist?
2. Can we measure it independently?
3. Can we prevent regressions and security escalation?
4. Does improvement reduce total human maintenance cost?
5. Does the improvement data compound into a moat?
6. Will developers choose our infrastructure rather than hyperscaler-native equivalents?
7. Can the same control plane work across coding, enterprise workflows, databases, websites and eventually physical systems?

Those questions will drive the next research passes.
