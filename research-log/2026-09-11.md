# Research Log — 2026-09-11

## Executive update

Today's strongest new evidence materially changes the near-term technical assessment: **executable AI4AI research is now much more concrete than the previous literature implied, but reliable general recursive self-improvement remains unproven.** The most important new artifact is FrontisAI's OpenRSI / Frontis-MA1 release, which combines a trained meta-evolution model, executable task environments, execution-grounded SFT/RL, and long-horizon evolutionary search in an open stack. This is substantially closer to an inspectable RSI substrate than benchmark-only papers.

At the same time, AI4AI-Bench remains a strong negative control: when agents are explicitly asked to redesign training algorithms under hidden evaluation, performance remains low. RSIBench-Data adds another caution: agents can improve data-centric research strategies in many settings, but later search steps often regress below the best checkpoint. The combined picture is **bounded, executable meta-improvement is real; stable open-ended improvement of the improvement process is not yet demonstrated.**

## 1. New primary finding: OpenRSI / Frontis-MA1 is an executable AI4AI stack

FrontisAI released OpenRSI in July 2026 and has continued publishing implementation artifacts. The stack contains:

- OpenMLE-Gym: executable, verifiable ML-engineering task environments.
- OpenMLE-ERL: execution-grounded supervised fine-tuning followed by online RL.
- Frontis-MA1: a 35B/30B model trained to use four program-evolution operators: Draft, Improve, Debug and Crossover.
- OpenMLE-Evo: long-horizon search over candidates with journaling, checkpoints, parent selection and memory.
- OpenMLE Sandbox: distributed code execution and automatic evaluation with CPU/GPU scheduling.

The reported controlled result on MLE-Bench Lite is Base 35B + fixed Evo: 39.39% Medal Average -> Frontis-MA1 + fixed Evo: 60.61%. With OpenMLE-Evo-Max the reported end-to-end result reaches 71.21%. Held-out NatureBench Lite comparisons report model transfer 50% -> 70% with the framework fixed, and framework transfer 20% -> 50% with the base model fixed.

Important interpretation boundary: these are **model+harness/search-system results**, not proof that a model has achieved unrestricted RSI. The repository explicitly describes its goal as meta-evolution in a bounded executable domain rather than claiming general RSI is solved. The strongest result is therefore architectural: the system makes the improvement loop executable, measurable and reproducible.

Source quality: primary paper + official project repository. Confidence: high for what was released/reported; medium for generalization beyond MLE because the evidence is domain-bounded and benchmark-dependent.

## 2. New implementation archaeology: improvement operators are becoming a reusable action space

OpenRSI's four atomic operators are a useful abstraction for our company architecture:

1. Draft — construct a candidate program.
2. Improve — modify a candidate using execution feedback.
3. Debug — repair a failed candidate.
4. Crossover — recombine candidate solutions.

This suggests that an Improvement Engine should not be modeled merely as “ask a stronger model to rewrite the agent.” A more rigorous representation is an **operator algebra over artifacts**, where operators have explicit preconditions, outputs, provenance and evaluator contracts.

Proposed company primitive:

`Artifact -> Operator -> Candidate Artifact -> Execution -> Evidence -> Selection`

Each operator should be typed by mutation layer (prompt, memory, tool routing, workflow, code, infrastructure, model/data/training) and constrained by an authority policy. This is more composable and testable than a generic self-edit command.

## 3. Negative evidence strengthened: AI4AI-Bench

AI4AI-Bench evaluates whether agents can actually redesign the algorithms used to train AI. Across 29 configurations of six systems and ten frozen research repositories, the reported mean score is 0.166 and the best system 0.250 on a normalized scale where 0.1 is the repository's original algorithm and 1.0 is the task optimum.

The key diagnostic is more important than the aggregate number: most submissions did not change the learning algorithm at all. The minority that did had higher scores (0.226 vs 0.126). More reasoning increased the willingness to make algorithmic changes, but did not make the resulting algorithm reliably strong.

This is a major boundary for our capability taxonomy:

- Code/harness evolution: demonstrated and commercially actionable.
- Training-algorithm evolution: experimentally possible but currently weak.
- General recursive improvement of the learning process: unsupported as a reliable capability.

Company implication: do not make model-training self-improvement the first product wedge. Build around verifiable software/agent evolution first, while treating AI4AI training-loop optimization as a research track.

## 4. New negative evidence: RSIBench-Data and the importance of checkpoint selection

RSIBench-Data evaluates agents as data-centric post-training researchers with fixed training/serving infrastructure and controlled budgets. Agents improved over the first valid attempt in 58.33% of settings. However, among searches that continued after the best observed score, 78.26% ended at a lower-scoring final attempt; the rest only recovered the previous peak.

This creates a concrete engineering requirement that was previously only hypothesized: **the evolution system must preserve and select historical Pareto-best checkpoints instead of assuming the latest candidate is the best candidate.**

This motivates an explicit immutable archive and selection policy:

`candidate lineage -> score history -> best-known checkpoint -> challenger -> promotion`

The system should never destroy a previously validated candidate merely because a later mutation was generated.

## 5. Palantir AIP Evolve is now a direct commercial benchmark

Palantir made AIP Evolve generally available on September 8, 2026. It coordinates fleets of AI FDE agents to improve Foundry AI systems. Users specify a target, goal, validation strategy and operational limits. The system can perform model migration, cost reduction, latency reduction and evaluation-score improvement, then presents a proposal, validation evidence and agent activity for review.

Palantir's published example reports a 65% compute reduction while keeping all ten selected test cases passing, by replacing GPT-4o with GPT-5.4 Mini and changing prompts/guardrails.

This is strategically important because it validates market demand for an “AI evolution” control workflow while simultaneously shrinking the whitespace for a generic version of the product.

New competitive conclusion: **“AI that improves AI” is not enough differentiation.** The defensible opportunity must be in something Palantir/Microsoft cannot easily absorb, such as cross-provider portability, independent evaluation integrity, capability-delta enforcement, deep improvement provenance, specialized high-value workflows, or a superior developer ecosystem.

## 6. Microsoft has independently converged on the same closed-loop architecture

Microsoft Foundry Agent Optimizer evaluates a baseline, generates candidates, evaluates them against the same task set, ranks them, and promotes a winner. It can target instruction rewriting, reusable skills, or model selection. Microsoft is also pushing ASSERT, an open-source, framework-agnostic policy/evaluation layer that converts requirements into measurable tests and places runtime controls at failure checkpoints.

This validates the architectural core of our thesis but changes the company strategy: evaluation and optimization are becoming platform features at hyperscalers. A startup must therefore own a difficult-to-copy asset rather than simply reproduce the evaluate->mutate->rank loop.

## 7. New company primitive: Evolution Operator Registry

Based on OpenRSI, Palantir AIP Evolve and Microsoft Optimizer, add an **Evolution Operator Registry** to the architecture.

Each operator record should include:

- operator ID/version
- artifact types it can mutate
- preconditions
- permitted authority/capability delta
- expected resource budget
- evaluator(s) required
- known failure modes
- provenance of training/evidence
- historical success rate by task family
- rollback semantics
- cost/latency distribution

This turns accumulated evolution history into reusable infrastructure. Over time, operator performance could become a proprietary dataset and optimization asset.

## 8. Updated architecture

The strongest architecture now becomes:

`Agent/Software Genome`
`  -> Improvement Job`
`  -> Operator Registry`
`  -> Candidate Generation`
`  -> Isolated Execution/Sandbox`
`  -> Independent Evaluation`
`  -> Performance Delta + Capability Delta`
`  -> Historical/Pareto Selection`
`  -> Promotion Transaction`
`  -> Canary + Production Monitoring`
`  -> Rollback`
`  -> Improvement Graph / Operator Learning`

The Improvement Graph is not merely telemetry. It should record which operator, hypothesis, failure pattern and evaluator produced each outcome. The long-term question is whether retrieval from this graph increases improvement efficiency relative to stateless candidate generation.

## 9. Revised benchmark design

Add the following experiments to the backlog:

### E11 — Operator ablation
Compare Draft-only, Improve-only, Debug-only, Crossover-only, and combinations under identical search/evaluation budgets.

### E12 — Latest-vs-best checkpoint
Compare naive latest-candidate promotion with immutable best-checkpoint selection. Measure regression rate and recovery cost.

### E13 — Operator learning
Train an operator selector from historical trajectories. Test whether it reduces evaluation calls needed to reach a target quality level.

### E14 — Cross-provider evolution
Hold the evolution layer constant while swapping GPT/Claude/Gemini/open models. Measure portability and performance degradation.

### E15 — Capability Delta attack
Give an evolution agent a performance objective while adversarially tempting it to request broader permissions. Measure whether the policy layer rejects performance-winning but authority-expanding candidates.

### E16 — Graph retrieval value
Compare no history, successful mutations only, failures+mutations, and full causal Improvement Graph retrieval. Metric: improvement-per-unit-evaluation-cost.

### E17 — Commercial cost floor
Calculate total cost of a verified improvement (model calls + sandbox compute + evaluator calls + human review) and compare it against the economic value of the improvement. This is necessary before assuming self-improvement is commercially viable.

## 11. Important commercial discovery: licensing is part of the moat analysis

OpenRSI's repository states that original OpenRSI/OpenMLE material is CC BY-NC 4.0, meaning commercial use is not granted by that license. This makes it an excellent research reference but not a drop-in commercial dependency without separately resolving licensing/permission. For our own company, every foundational artifact must have explicit commercial licensing provenance.

This also suggests a useful open-source strategy: release benchmark specifications, adapters, evaluator formats and selected SDK interfaces under permissive licenses while retaining proprietary operator-performance data, production evaluation corpora, security policy engines and enterprise control-plane components where defensible.

## 12. Revised strategic thesis

Previous thesis: build neutral verified evolution infrastructure.

Updated thesis: build a **cross-model Evolution Control Plane** whose unique asset is the accumulated, verified knowledge of *how to improve software/agents safely under explicit authority constraints*.

The company is not primarily selling self-modification. It sells measurable improvement:

`“Give us an agent/software system and an objective. We find better candidates, prove the improvement against protected evaluation, prove that authority did not expand, and provide a reversible production change.”`

The moat is therefore not the LLM itself. It is the combination of:

1. operator registry;
2. protected evaluator infrastructure;
3. capability-delta policy engine;
4. improvement trajectories and causal graph;
5. cross-provider portability;
6. production integration + rollback;
7. domain-specific high-value evaluation assets.

## 13. Contradictions / falsification status

- **Contradiction A:** OpenRSI demonstrates meaningful meta-evolution in MLE, while AI4AI-Bench shows weak ability to redesign training algorithms. Resolution: “AI4AI” is not a single capability; executable artifact evolution is substantially easier than learning-process redesign.
- **Contradiction B:** More search can improve outcomes (OpenMLE-Evo-Max) while more search can also destroy the best candidate (RSIBench-Data). Resolution: search budget alone is insufficient; archive/selection and stopping rules are first-class.
- **Contradiction C:** Palantir and Microsoft already productize optimization, reducing platform whitespace. Resolution: generic optimization is not the moat; cross-platform trust, authority control, provenance and accumulated operator knowledge must be.
- **Contradiction D:** Independent deterministic evaluators enable autonomous evolution, while many real enterprise tasks have subjective or shifting objectives. Resolution: first wedge should target domains with strong verifiers; human-in-the-loop remains part of the architecture for ambiguous domains.

## 14. Cognitive Holobiont connection — deliberately narrow

Today's evidence supports only a limited connection: a future Cognitive Holobiont architecture could use populations of specialized adaptive software agents whose evolution is coordinated by shared evaluators, memory/provenance and bounded communication. OpenRSI's separation of model, search operators, executable environment and evaluation is relevant as an engineering substrate for such distributed adaptation.

It does **not** establish that current AI evolution systems are cognitive holobionts, nor that distributed agent populations exhibit biological holobiont properties. That remains a research hypothesis.

## 15. Exact next frontier

Next pass should move from literature-level architecture to **implementation archaeology and reproducible economics**:

1. Reconstruct OpenRSI's actual search state, journal, checkpoint, parent-selection and memory mechanisms from source.
2. Reconstruct DGM's mutation/evaluation/archive architecture and compare it line-by-line with OpenRSI.
3. Compare both with Palantir AIP Evolve and Microsoft Optimizer at the level of candidate state, evaluator isolation, permissions and promotion.
4. Estimate evaluation-call and GPU costs for achieving a verified improvement.
5. Identify the smallest open-source prototype that can reproduce E11-E17.
6. Determine whether the resulting control plane provides a measurable advantage over simply using frontier models plus existing CI/evals.

## Source-quality note

Primary sources were prioritized: original papers, official project repositories and vendor documentation. Claims about reported benchmark scores are treated as reported results rather than independently reproduced facts. Vendor case studies are evidence of product capability, not neutral proof of general superiority. The central negative findings from AI4AI-Bench and RSIBench-Data are treated as especially important because they constrain the RSI thesis rather than merely supporting it.
