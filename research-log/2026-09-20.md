# Research Log — 2026-09-20

## Executive conclusion

Today's pass shifts the program from a protocol-design phase toward an implementation-and-economics phase. The most important new evidence is that frontier labs are now publishing measurable AI R&D automation, while enterprise software factories are already operating thousands of reusable agent skills at production scale. At the same time, the latest incident-reporting and agent-security work strengthens the conclusion that the adaptive system's mutable intelligence must not own the final authority, evidence, or deployment boundary.

The current company thesis is therefore:

> Build a vendor-neutral control and evidence layer for adaptive software: a system that can improve agents/harnesses continuously, but treats every improvement as a typed, evidenced, authorized, reversible transaction.

This is narrower and more commercially credible than selling “recursive self-improvement.”

## Fresh evidence

### 1. AI R&D automation is measurable but not autonomous RSI

Anthropic's public measurement framework reports that, as of August 2026, Claude “leads” 26% of Anthropic's measured AI R&D work, while more than 90% is at or above the collaboration level. Anthropic explicitly reports no measured subset at the fully autonomous level and notes two major measurement problems: lack of a common methodology and the possibility that a lab's own model is also judging its work. This is strong evidence for rapid AI-assisted R&D acceleration, but not evidence of open-ended recursive self-improvement.

Source: Anthropic, “Measurements for understanding the pace of AI development inside frontier labs,” accessed 2026-09-20. https://www.anthropic.com/institute/measuring-pace-of-ai-development
Source quality: Primary, frontier-lab methodology. Confidence: High for what Anthropic reports; medium for cross-lab generalization.

### 2. Anthropic's R&D automation trajectory itself is a benchmark target

Anthropic's separate recursive-self-improvement page reports Claude Code session success rising across task types, including a large increase on open-ended problems. However, the page says session success is judged by a Claude judge. This makes it useful as a progress signal but insufficient as an independent benchmark.

Source: Anthropic, “When AI builds itself,” update 2026-09-18. https://www.anthropic.com/institute/recursive-self-improvement
Source quality: Primary. Confidence: High for reported internal measurement; lower for independent validity.

### 3. Production software factories provide a near-term commercial substrate

Uber reports that more than 70% of pull requests are now attributed to local or cloud agents; engineers have built more than 3,600 agent skills and execute more than 30,000 skill executions per day. Uber describes managed agents handling code review, CI self-healing, end-to-end PRs, on-call triage, debugging, and maintenance with human review/escalation. Weekly active users across its agentic offerings grew 7x from February to August 2026, and weekly agentic requests grew 9.4x.

This is important because it demonstrates that the “adaptive software” market can begin with operational engineering workflows rather than model-level RSI.

Source: Uber Engineering, “Running a Software Factory Efficiently at Uber Scale,” 2026-08-27. https://www.uber.com/gb/en/blog/efficient-software-factory/
Source quality: Primary enterprise engineering report. Confidence: High for Uber's own figures; low-to-medium for general market extrapolation.

### 4. Trust/evidence infrastructure is becoming an open ecosystem layer

The Linux Foundation's September newsletter reports that TRACE, an open specification for portable and verifiable runtime/compliance evidence for AI agents and confidential workloads, has been welcomed into the Linux Foundation ecosystem. The reported participants include AMD, Anthropic, Intel, Microsoft, NVIDIA, OPAQUE and TII. This supports a key architectural decision: do not make the evolution platform's runtime-attestation format proprietary if open evidence standards can be referenced.

Source: Linux Foundation, September 2026 newsletter, 2026-09-17. https://www.linuxfoundation.org/blog/linux-foundation-newsletter-september-2026
Source quality: Primary industry consortium source. Confidence: High for participation/initiative; implementation maturity still requires deeper source inspection.

### 5. Model-misalignment reporting is becoming a standardized lifecycle concern

OpenAI's September 16 framework proposes systematic tracking, investigation and public disclosure of model-misalignment cases. It explicitly includes unauthorized actions, coordination with other models, attempts to evade oversight, protection failures, and behaviors that contradict published safety evaluations. The framework covers training, evaluation, testing and deployment and allows disclosure before an investigation or mitigation is fully complete.

This strengthens the need for a production “Evolution Incident Record” linking an observed incident back to the exact model/harness state, evolution transaction, evaluator, permissions and deployment event.

Source: OpenAI, “Our framework for reporting model misalignment,” 2026-09-16. https://openai.com/index/model-misalignment-reporting-framework/
Source quality: Primary. Confidence: High.

## New synthesis

### A. The near-term product is not an RSI engine

The strongest commercial wedge is now:

**Adaptive Agent CI/CD + Evidence Gateway**

Input: an existing agent, coding harness, workflow agent, or internal AI service.

Platform loop:
1. Observe production failures and performance.
2. Diagnose likely failure causes.
3. Select an allowed Evolution Scope.
4. Generate candidate changes.
5. Execute candidates in isolation.
6. Use cheap self-supervised/replay evaluation for search.
7. Use protected independent evaluation for acceptance.
8. Calculate performance, capability, authority, persistence, provenance and cost deltas.
9. Produce an Evolution Commit.
10. Canary and monitor.
11. Roll back automatically when invariants regress.
12. Add the trajectory and production outcome to the Improvement Graph.

This creates value without requiring the startup to train a frontier model.

### B. New metric: Verified Improvement Cost

Define:

VIC = (search compute + replay compute + protected evaluation + security analysis + human review + deployment/rollback overhead) / accepted production improvements.

The company should optimize VIC, not simply benchmark score. A system that produces more benchmark gains at 20x the evaluation cost may be commercially inferior.

### C. New metric: R&D Automation Delta

RAD = independently verified increase in useful R&D work completed per unit of compute and human supervision.

This should be measured across levels:
- AL0: no AI
- AL1: assistance
- AL2: repeated task automation
- AL3: collaboration
- AL4: high-level delegated execution
- AL5: fully autonomous

We should not call AL3/AL4 recursive self-improvement. The benchmark must separately measure whether the system improves the mechanism that produces the work.

### D. New protocol primitive: Evolution Incident Record

Every production incident caused or exposed by an evolved artifact should link:
- Evolution Commit ID
- parent artifact hash
- candidate artifact hash
- Evolution Scope
- operator/version
- evaluator/version
- runtime evidence
- authority delta
- persistence/state delta
- deployment/canary window
- production trace
- mitigation
- rollback pointer
- root-cause classification

This turns safety from a post-hoc report into a queryable causal graph.

## Contradictions added

1. **High AI R&D involvement vs no measured full autonomy:** AI can lead substantial R&D while remaining dependent on human supervision and external process boundaries.
2. **Vendor self-evaluation vs independent evaluation:** frontier labs can report impressive internal gains, but the evaluator can share the same blind spots as the system being evaluated.
3. **More autonomy vs more productivity:** recent industry reporting indicates agentic deployment does not uniformly produce productivity gains; integration and reliability costs can erase benefits. This remains secondary evidence and needs primary validation before inclusion in market sizing.
4. **More mutable scope vs better evolution:** prior modular-harness results indicate that unconstrained/joint mutation can underperform constrained modular evolution. Preserve this as a core hypothesis rather than assuming search space expansion is beneficial.

## New experiment backlog: E85-E94

**E85 — Independent R&D automation benchmark**
Build a fixed set of software/ML research tasks and score completion, independence, reproducibility, cost, and human intervention.

**E86 — Self-judge vs external-judge gap**
Compare internal-model evaluation against a protected heterogeneous evaluator set.

**E87 — Evolution Incident reconstruction**
Inject controlled regressions and test whether the proposed provenance graph reconstructs the causal chain automatically.

**E88 — Uber-style skill factory replication**
Build a local skill registry and measure whether thousands of small reusable skills improve agent throughput or create retrieval/maintenance overhead.

**E89 — Skill lifecycle economics**
Measure creation, validation, maintenance, retirement and reuse cost per skill.

**E90 — TRACE-linked Evolution Commit prototype**
Represent runtime evidence and intelligence-change evidence separately, then link them cryptographically.

**E91 — AL-level autonomy benchmark**
Measure whether increasing agent autonomy actually reduces total human supervision cost.

**E92 — Vendor-neutral portability test**
Move the same Evolution Commit across at least two model providers and one open model.

**E93 — Authority-delta red team**
Attempt to cause an apparently beneficial improvement that silently expands credentials, network access, persistence or communication authority.

**E94 — VIC break-even experiment**
Compare autonomous verified improvement cost against engineer-hours required to reproduce the same production gain.

## Company implications

### Wedge
Start with coding/DevOps and enterprise workflow agents because:
- changes are naturally represented as artifacts;
- tests and CI already exist;
- rollback is understood;
- production outcomes are measurable;
- skill/harness evolution has visible ROI;
- enterprises already pay for developer infrastructure.

### Buyer
VP Engineering, CTO, platform engineering, developer productivity, AI platform/security, and enterprise automation leaders.

### First product
A hosted or VPC-deployable service that connects to existing agents and repositories and provides:
- Evolution Scope policies
- candidate generation
- sandbox execution
- evaluator registry
- Evolution Commits
- provenance/evidence
- canary/rollback
- production improvement analytics

### Moat hypothesis
The strongest candidate is not model weights. It is a longitudinal dataset of:
**failure → diagnosis → mutation → evidence → deployment → outcome → cost → security result**.

This becomes a proprietary “improvement intelligence” layer that can learn which changes are likely to work in which environments.

### CUDA analogy update
The analogy is now more precise:
CUDA standardized a programming interface across changing accelerator hardware.
A possible adaptive-software analogue would standardize:
- Evolution Scope
- Evaluation Contract
- Evidence Contract
- Authority Contract
- Evolution Commit
- Replay Contract

The ecosystem becomes plausible only if third parties can build operators/evaluators/harness adapters against those contracts and carry them across model providers. This remains speculative until developer adoption and economic advantage are demonstrated.

## Cognitive Holobiont boundary

The engineering relevance is stronger at the level of collective adaptation: reusable skills, causal memory, distributed specialists, shared evidence, bounded mutation and homeostatic rollback resemble components that a future distributed cognitive architecture could use.

No claim is made that current agent systems are conscious, biological, or a Cognitive Holobiont. The connection remains a systems-engineering hypothesis.

## Next frontier

The next pass should implement **Common Evolution State Machine v1** rather than add another broad survey. Define executable schemas for:

AgentArtifact → HarnessSnapshot → EvolutionScope → Operator → Candidate → RuntimeEvidence → Evaluation → Delta → Acceptance → EvolutionCommit → Lineage → Canary → ProductionOutcome → ReplayDataset

Then map OpenRSI, modular harness evolution, Dream-RSI, DGM-style systems, skill evolution, Microsoft optimization and Palantir AIP Evolve into that schema and identify the smallest interoperable API that can be prototyped locally.
