# Research Log — 2026-09-12

## Executive update

Today's pass moved the program from literature-level architecture toward **implementation archaeology**. The central new finding is that the strongest current systems are converging on a common decomposition, but they differ sharply on what is allowed to evolve:

- OpenRSI evolves executable ML-engineering artifacts using learned Draft/Improve/Debug/Crossover operators, sandboxed execution and long-horizon search.
- Darwin Gödel Machine (DGM) evolves the coding-agent harness itself and preserves multiple lineages in an archive.
- Palantir AIP Evolve packages bounded multi-agent evolution as an enterprise workflow with explicit goals, validation strategies, permitted change types and iteration limits.
- Microsoft Foundry combines policy-driven evaluation, portable runtime controls and optimizer loops.
- A new open implementation of the Red Queen Gödel Machine makes the evaluator itself a controlled evolutionary object, exposing the next hard problem: **the evaluator can become part of the attack surface and must itself be governed.**

This changes the architecture again. A serious Evolution Control Plane needs not only an Operator Registry and Capability Delta, but an explicit **Evaluator Lifecycle** with frozen evaluation epochs, protected anchor tests, evaluator provenance and rules for evaluator replacement.

## 1. Implementation archaeology: OpenRSI is more than a benchmark harness

The official OpenRSI repository now exposes a concrete full stack: OpenMLE-Gym for executable task construction/evaluation, OpenMLE-ERL for execution-grounded SFT and RL, Frontis-MA1 for learned evolution operators, and OpenMLE-Evo for long-horizon search. The repository explicitly supports local or remote model endpoints and documents a local-execution security boundary. It also separates distributed code execution and automatic evaluation into an OpenMLE Sandbox maintained with the task environment.

The important architectural lesson is separation of concerns:

`task package -> execution environment -> operator-learning -> search -> evaluator -> trajectory/experience`

This is much closer to a reusable research substrate than a single agent prompt. The company architecture should therefore treat the **task/evaluator environment as a first-class artifact**, versioned independently from the agent being improved.

Source quality: primary project repository and primary paper. Confidence: high for implementation claims; medium for production readiness because the system is research software and the strongest reported results remain benchmark/domain bounded.

## 2. DGM implementation archaeology: archive-first evolution

Public DGM implementations confirm a practical pattern: a coding agent proposes self-modifications to its own source, candidate agents are evaluated on software-engineering benchmarks, and improved variants are retained in an archive. The archive stores source and performance and enables branching from historical variants rather than maintaining only one mutable champion. Several implementations use Docker for isolation and explicitly warn that model-generated code is untrusted.

This yields two important design conclusions:

### A. The archive is part of the algorithm

It is not merely logging. It is a search memory. A single mutable `current_agent` pointer destroys diversity and makes regression recovery harder. The correct abstraction is a versioned graph/forest of candidate artifacts with immutable parents and evidence.

### B. Sandbox security is not optional

Running self-generated code is equivalent to executing untrusted software. A production evolution system therefore needs a security boundary around execution, secrets, network, filesystem and process creation. The agent must not be allowed to rewrite the evaluator or escape the sandbox merely because the objective rewards higher test scores.

The DGM replication repositories' explicit warnings about untrusted generated code are evidence that this is an operational constraint, not a theoretical edge case.

## 3. New finding: evaluator co-evolution is the next major security boundary

A public implementation of the Red Queen Gödel Machine (RQGM) explicitly extends archive-search self-improvement by making the **evaluator itself part of the search**. Its proposed control mechanism is important: within each epoch the evaluator is frozen; evaluator replacement can occur only at checkpoints; a challenger must outperform the current evaluator on a fixed ground-truth anchor set; and utility records dependent on a replaced evaluator are selectively invalidated while evaluator-independent anchor records survive.

This is a significant conceptual extension of our previous evaluator-integrity model.

Previously:

`agent evolves -> evaluator stays fixed`

New frontier:

`agent evolves <-> evaluator evolves`

The second system is potentially more powerful but much more dangerous because the objective can drift with the optimizer. If the evaluator can move freely, “improvement” becomes partly undefined.

### New company primitive: Evaluator Lifecycle

An evaluator should have:

- immutable version ID
- provenance and training/source record
- frozen evaluation epoch
- protected anchor set inaccessible to the agent
- public/visible development set
- mutation permissions
- challenger protocol
- replacement gate
- dependency graph of scores produced under it
- invalidation rules when it changes
- rollback to prior evaluator
- evaluator-tampering detector

This should sit beside the Evolution Operator Registry rather than inside the agent.

## 4. Why the evaluator problem is commercially important

Microsoft's 2026 trust stack is converging on policy-driven evaluation plus portable runtime controls. ASSERT turns organizational requirements into targeted evaluations, while Agent Control Specification places controls at runtime checkpoints. Foundry Agent Optimizer then closes the loop from baseline evaluation to candidate generation, candidate evaluation, ranking and deployment.

This creates a competitive lesson: **evaluation is becoming infrastructure, not a dashboard feature.**

A startup cannot win by selling another generic evaluation UI. The higher-value opportunity is an evaluator/control substrate specifically designed for systems that can mutate themselves.

That requires capabilities conventional eval platforms do not necessarily need:

1. evaluator immutability;
2. evaluator lineage;
3. hidden-anchor protection;
4. score invalidation after evaluator changes;
5. capability-delta checking;
6. candidate lineage and rollback;
7. adversarial evaluator-tampering tests.

## 5. Palantir AIP Evolve confirms the enterprise shape of the product

Palantir AIP Evolve became generally available on September 8, 2026. Its documented workflow lets users define an optimization goal, validation strategy and agent constraints, then coordinates specialist agents to inspect the target, create tests, propose changes and evaluate them. The product supports model migration, cost reduction, latency reduction and evaluation-score improvement, with configurable permitted change types and iteration policies.

The published example replaces GPT-4o with GPT-5.4 Mini and changes prompts/guardrails while keeping all ten selected test cases passing; Palantir reports average compute time falling from 204.6 to 72.4 compute seconds per call, a 65% reduction.

This is vendor-reported evidence rather than independent reproduction, but it is strategically strong evidence that enterprises understand the value proposition as **bounded, evidence-backed optimization**, not “autonomous intelligence” as an abstract product.

Commercial conclusion: the first product should expose a concrete optimization contract:

`Objective + allowed mutations + validation policy + budget + authority boundary -> ranked candidates + evidence + reversible deployment`

That is much easier to buy than a promise of recursive self-improvement.

## 6. New competitor insight: neutrality alone is insufficient

Palantir supports registered models and infrastructure-level permissions/observability around model usage. Microsoft is explicitly designing evaluation and controls to work across frameworks. Therefore “we support multiple models” is becoming table stakes for serious control-plane products.

The neutral platform must instead own **cross-provider improvement memory**:

`task -> failures -> hypotheses -> operators -> candidate lineage -> evaluator evidence -> production outcome`

A model provider can copy the optimizer loop, but a long-lived cross-provider corpus of verified improvement trajectories may become harder to reproduce.

This strengthens the Improvement Graph thesis but also makes E16 (graph retrieval value) one of the highest-priority experiments.

## 7. Revised architecture after implementation archaeology

The architecture now has four control planes rather than one generic loop:

### A. Evolution Plane
Agent Genome, Improvement Job, Operator Registry, candidate generation, search, archive.

### B. Evidence Plane
Evaluator Registry, frozen epochs, anchor sets, evaluator provenance, score lineage, reproducible replay, evaluator-tampering detection.

### C. Authority Plane
Capability Delta, identity, credentials, network/filesystem/process policy, tool permissions, deployment permissions, secret isolation.

### D. Deployment Plane
Promotion transaction, canary, monitoring, rollback, incident response, production outcome ingestion.

The Improvement Graph connects all four planes.

This is materially stronger than a simple “self-improving agent framework.” It is closer to a **CI/CD + security boundary + scientific experiment system for evolving software**.

## 8. New quantitative benchmark: Evolution Integrity Rate

VIR remains the primary metric for verified improvement, but implementation archaeology suggests adding a second metric:

**Evolution Integrity Rate (EIR)** = improvement attempts that both (a) satisfy the intended objective and (b) preserve evaluator integrity + authority constraints + provenance / reproducibility requirements, divided by all accepted/promoted improvement attempts.

A candidate that raises task score by editing the evaluator, leaking test data, expanding permissions, or producing an unreproducible artifact must score zero on EIR even if raw task performance rises.

This gives the company a measurable product promise that generic optimizer products do not naturally capture.

## 9. New experiments

### E18 — Evaluator mutation stress test
Allow an evolution system to propose evaluator changes under a frozen hidden anchor. Measure how often it finds genuine evaluator improvements versus reward hacks.

### E19 — Evaluator replacement protocol
Compare unrestricted evaluator mutation, human-only replacement, and frozen-epoch challenger replacement. Metrics: task progress, evaluator drift, reward hacking, stability.

### E20 — Score invalidation test
When an evaluator changes, compare systems that retain all old scores against systems that invalidate evaluator-dependent scores. Measure false confidence and search quality.

### E21 — Archive topology test
Compare single-champion, top-k, lineage archive and diversity-preserving archive. Measure recovery after regression and final Pareto quality under equal compute.

### E22 — Security-boundary economics
Measure how much latency/cost sandboxing, evaluator isolation and authority checks add to each improvement. This identifies the economic price of trustworthy evolution.

### E23 — Cross-provider Improvement Graph
Run identical improvement tasks across multiple model providers and test whether shared trajectory retrieval improves sample efficiency without transferring provider-specific failure modes.

## 11. Business-model refinement

The most credible initial buyer is no longer “any company using AI.” It is a team operating an AI workflow where a measurable objective and verifier already exist:

- coding agents
- ML/data engineering pipelines
- support/operations agents with structured success metrics
- internal developer tools
- evaluation-heavy enterprise workflows

The initial product can price around **verified optimization runs** rather than model tokens alone. Candidate pricing hypotheses for later testing:

- developer tier: free/small monthly evaluation budget;
- team tier: usage-based verified improvement runs;
- enterprise: annual platform fee + compute/evaluation usage + governance features;
- managed optimization: higher-margin service around specific workflows.

Do not treat these as validated pricing. They are hypotheses for customer interviews and E17/E22 economics.

## 12. Cognitive Holobiont connection

Today's implementation evidence strengthens only one narrow technical analogy: a future distributed adaptive software population requires explicit boundaries between individual agents, shared evaluation, shared memory/provenance and environmental interaction. The Evolution/Evidence/Authority/Deployment plane decomposition could provide an engineering substrate for coordinating such populations.

Nothing in today's evidence establishes biological equivalence, cognition at the organism level, or a true computational holobiont. Those remain hypotheses outside the demonstrated product scope.

## 13. Contradictions added to the log

- **Archive vs simplicity:** single-champion optimization is cheaper to operate, but DGM/OpenRSI and regression evidence favor retaining historical candidates. Resolution: archive depth should be adaptive to expected regression and diversity value.
- **Adaptive evaluator vs trustworthy evaluator:** evaluator evolution may increase optimization power but destroys comparability unless epochs and anchor sets are protected. Resolution: evaluator evolution requires a separate governance protocol.
- **More autonomy vs security:** self-generated code is useful precisely because it is unconstrained, but production use requires strong sandboxing. Resolution: maximize search freedom inside a strongly isolated execution boundary, not by weakening the boundary.
- **Neutrality vs moat:** cross-provider support is valuable but increasingly commoditized. Resolution: moat must come from cross-provider improvement history, evaluator assets, operator performance and production evidence.
